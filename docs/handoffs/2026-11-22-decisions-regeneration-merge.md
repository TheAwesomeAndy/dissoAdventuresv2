## Decisions made

- **Regenerate every record after the refactor, rather than argue that formatting
  cannot change a result.** The comparison is cheap to state and hard to dispute. The
  alternative, relocking the records against reformatted code without a rerun, would
  have left the lock asserting something nobody had checked.
- **Match the original BLAS thread count instead of accepting a tolerance.** One record
  differed under four threads. Rerunning with the original two reproduced it exactly,
  which separates "the code changed" from "the arithmetic was partitioned differently".
  A tolerance would have hidden which of the two it was.
- **Do not pin the thread count inside the runners.** That would edit frozen files and
  could move the committed values by one observation. The setting is recorded per
  record and in every new provenance block instead.
- **Participant-keyed files left in place**, by the owner's decision. Nothing was
  removed and no history was rewritten.
- **The paper's own repository was not consulted**, by the owner's instruction. The
  paper is a citation only.

## Findings

- **Verified.** Values that pass through the row-space readout fit depend on the BLAS
  thread count at the level of one observation. `experiments/v2/v2_baseline_input.json`
  with four threads differs from the two-thread record in 213 of 1,213 values, by at
  most 0.24 points. Two four-thread runs agree with each other exactly. One row tested
  directly reproduces the record with two threads and gives a different, mutually
  identical result with one and with four. No conclusion depends on it.
- **Verified.** Tuning the readout for every representation does not change the
  ordering of reservoir code, six-bin amplitudes and raw ERP-16
  (`V2_UPGRADE.md`, conclusion 7).
- **Verified.** The CI type check must use a numpy that exists for CI's Python. A pin
  to a release that needs Python 3.12 made the tests job fail before it ran any test,
  for several pushes.
- **Suspected, not tested.** The same thread sensitivity probably exists in the v1
  confirmatory pipeline's direct fit, at a similar size.

## Known limitations

- The thread count that reproduces a record is documented, not enforced. Running a
  command without its thread prefix can give a record that differs in the second
  decimal place.
- The regenerated records were produced on one machine type (OpenBLAS, SkylakeX
  kernel). A different BLAS kernel may differ in the same way a different thread count
  does.
- The tuned-readout experiment used z-scored input, to match the headline table. It was
  not repeated on input without z-scoring.
- The background jobs of this session were killed once by a container restart. The
  interrupted run was repeated in full; two cache files written just before the restart
  were deleted and recomputed.
